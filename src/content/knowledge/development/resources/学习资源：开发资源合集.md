3. 以下则是[^一套提示词]，用于限制agent 懂得参考成熟框架，不重复造轮子，据说水平是从一个 benchmark 的分数从 79% 提到了 100%。






[^一套提示词]:
  1. 不保留向后兼容。过时的直接删，别加兼容层、别写migration、别留fallback。
  2. 选能满足当前需求的最简单实现。不要预防性抽象，不要多此一举的配置层。
  3. 系统分层长。先跑通一个最小的端到端版本，再往上加东西。绝不为了未完成的复杂度拆掉能跑的东西。
  4. 组件保持模块化，关注点分离。
  5. 优先用成熟的、有人维护的库。没有明确理由别自己重写。
  6. 先翻项目里已有的依赖能做什么，再考虑加新包或自己写。别上来就假设库里没有。
  7. 架构决策往长了做。不接受"先这样以后再换"的临时方案。
  8. 先看成熟产品怎么解决同一个问题，用已验证的模式，别从零发明。

[^四款浏览器连接器]:

  - “CUA drive” → `Cua Driver`
  - “Open Cli” → `jackwener/OpenCLI`，不是另一个做本地 MLX 感知的 `opencli.run`
  - “Egolite” → `ego (lite)`
  - “Kimi web bridge” → `Kimi WebBridge`

  核心结论：CDP 不是唯一的“外部连接方式”，但其中几个工具内部仍然会使用 CDP。区别在于：你是否需要自己启动调试端口、是否连接当前 Chrome、以及 Agent 是否有独立工作空间。

  | 工具 | 连接方式 | 能否接当前 Chrome | 更适合 |
  |---|---|---|---|
  | Cua Driver | macOS 原生辅助功能、屏幕捕获、像素输入；浏览器页面使用经过校验的 CDP 路由 | 可以，但需要明确授权 existing profile | 全桌面、后台操作、浏览器和原生 App 混合 |
  | OpenCLI | Chrome 扩展 + 本地 daemon + WebSocket | 可以，支持绑定手动打开的标签页 | 当前 Chrome、登录态复用、CLI/Agent 自动化 |
  | ego (lite) | 自带 Chromium + `ego-browser`，内部通过 CDP 控制 | 不能直接控制现有 Chrome；会迁移 Chrome 数据到自己的浏览器 | 人和 Agent 并行工作、隔离 Space |
  | Kimi WebBridge | 浏览器扩展 + 本地服务，内部通过 CDP 操作 Chrome/Edge | 可以，复用现有登录状态 | Kimi Work、Kimi Claw 或其他本地 Agent |

  ### 1. Cua Driver

  这是最接近“真正 Computer Use”的方案。它可以操作 macOS 原生 App，也可以操作 Chromium 页面，并通过窗口 PID、窗口 ID 和浏览器 tab 做精确绑定。官方支持 MCP、CLI、Codex、Claude Code 等接入。macOS 需要 Accessibility 和 Screen Recording 权限。

  它的浏览器路线并不是单纯的截图点击：对于准确绑定的非活动页面，它使用 CDP 做后台导航、DOM 输入和页面操作；原生 App 则使用系统级能力。因此它减少了“手动启动 CDP”的麻烦，但并没有完全摆脱 CDP。

  优点是能力最广，能操作浏览器、桌面 App、Canvas、Electron 等；缺点是安装和权限配置最复杂，而且连接现有 Chrome profile 会暴露该 profile 的页面、Cookie、Storage 和网络能力，需要显式授权。

  ### 2. OpenCLI

  这是我认为与你当前需求最匹配的工具。

  它用 Chrome 扩展和本地 daemon 连接普通 Chrome，不要求你手动用 `--remote-debugging-port` 启动 Chrome。它支持：

  - 绑定已经手动打开的标签页；
  - 复用 Chrome 登录状态；
  - 读取结构化 DOM；
  - 点击、输入、滚动、提取；
  - 网络请求捕获；
  - 为网站编写稳定的 CLI adapter。

  典型结构是：

  ```text
  Agent / opencli
        ↕ localhost WebSocket
  OpenCLI daemon
        ↕ Chrome Extension API
  Chrome
  ```

  官方文档明确支持 `opencli browser <session> bind` 来绑定现有标签页，并用稳定 session 继续多步操作。

  需要注意的是，OpenCLI 的本地 daemon 端口没有内置认证，官方明确警告不要把它直接暴露到局域网或公网；如果远程 Agent 要使用，应通过 SSH 反向隧道。

  ### 3. ego (lite)

  `ego (lite)` 不是 Chrome 连接器，而是一个专门给 Agent 使用的 Chromium 浏览器。

  它首次启动时可以迁移 Chrome 的登录状态、Cookie、扩展和书签，然后给每个 Agent 一个独立的 Space。你继续使用自己的标签页，Agent 在另一个 Space 里工作，互不抢焦点。

  它的 `ego-browser` 运行时仍然通过 CDP 控制自己的 Chromium，但你不需要自己处理 CDP 端口。它目前主要支持 macOS，适合：

  - 不想让 Agent 改动当前 Chrome 标签页；
  - 需要多个浏览任务并行；
  - 希望保留登录状态，同时把 Agent 操作隔离开。

  它不适合“直接操作我当前这个 Chrome 窗口”。本质上是“迁移到一个 Agent 专用浏览器”，不是连接现有 Chrome。

  ### 4. Kimi WebBridge

  Kimi WebBridge 是一个浏览器扩展加本地桥接服务，可以控制现有 Chrome 或 Edge，支持导航、点击、表单输入、截图、内容提取和登录态复用。它既能配合 Kimi Work，也支持 Claude Code、Codex、Cursor、Kimi Code、Hermes Claw 等本地 Agent。

  它的底层仍然是本地服务调用 Chrome DevTools Protocol，但你不需要直接管理 CDP 端口。官方声称登录状态和页面内容都在本机处理。

  缺点是它更像“某个 Agent 的浏览器连接器”，公开的底层 CLI/API 和可扩展性不如 OpenCLI；官方 FAQ 也提到，其他扩展可能导致 snapshot、evaluate、screenshot 或 click 失败。

  ### 我的推荐顺序

  如果目标是“让我这个 Agent 操作你当前已经登录的 Chrome”：

  1. OpenCLI：最直接，扩展桥接、可绑定现有标签页、适合 Agent 和 CLI。
  2. Kimi WebBridge：也能连接当前 Chrome，但更偏 Kimi 生态。
  3. Cua Driver：如果还要操作桌面 App、后台窗口或复杂 GUI，能力最强，但配置和安全边界更重。
  4. ego (lite)：如果你接受使用一个独立的 Agent 浏览器，它的并行 Space 体验最好；但它不是当前 Chrome 的直接连接方案。

  所以，你的判断是对的：CDP 不是唯一方案。对我们这个场景，最值得优先试的是 OpenCLI；它可能正好解决“需要手动启动 CDP Chrome”这个问题。
